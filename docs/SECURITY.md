# Security controls

What protects the deployed app, and in particular `POST /api/review`, the one route that spends money (D20). The right-hand column maps each control to the SOC 2 Trust Services Criteria it serves, to show what an auditor would look for.

SOC 2 is an independent attestation of an organisation's controls over a period of time. A repository cannot be SOC 2 certified on its own. Organisation-level controls are outside this repository and are listed at the end.

## What the review endpoint can and cannot do

- **Can:** run the fixed review pipeline (`src/core/review`) on one plan, with the server's model, prompt, JSON schema, token limit and time budget, and return the review.
- **Cannot:** choose the model, send its own prompt or messages, or reach any other OpenRouter feature. The request schema is strict: one field, `plan`. A leaked token can therefore only review plans, at most 200 a day.

## Operating it

- **Rotate the token:** generate a new one, put its hash in `review.env`, and run `docker compose up -d` (docs/DEPLOY.md). The old token stops working immediately.
- **Rotate or revoke the key:** replace `openrouter_api_key` and restart, or revoke the key at OpenRouter. Either way the endpoint fails closed.
- **Read the audit trail:** `docker logs plan-reviewer-web-1 | grep review_request`.
- **Turn the endpoint off:** remove `review.env` and restart. The page and the scheduling API are unaffected.
- **Incident:** revoke the key at OpenRouter first (it stops spending), then rotate the token, then read the audit lines for the request ids and client addresses involved.

## Outside this repository

SOC 2 also needs organisation-level controls: access reviews for the server and the GitHub repository, a written incident response and on-call process, vendor review of OpenRouter and the model provider (their data retention and training policies), background checks, security training, backups, and evidence that all of these ran over the audit period. None of those can live in code.
